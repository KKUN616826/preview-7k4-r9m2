Clock conditions

Dynamic tasks depend on whether the world waits while the model thinks. The two conditions are recorded and tabulated separately.

Continuous clock

The environment and external events keep advancing while the model reasons or waits for an API response. The robot follows a declared hold policy until a new command arrives.

Supports
Real-time control claims
Matters for
Moving targets, timing windows

Paused inference

Simulated time stops while the model computes. This isolates task reasoning from latency, but it does not support a real-time-control claim.

Supports
Reasoning diagnosis
Not for
Claims about control speed

No effective action rate is inferred from simulator throughput or from controller interpolation inside a chunk.

Status. Budgets, episode counts, seeds and tolerances are fixed for each evaluation round before any system is run, and are published with that round's results. Until then they are listed as pending; they are never chosen after seeing model rankings.

Different interfaces. Same scoring standard.

Every system is run on the same task configurations, scored by the environment rather than by itself, and reported together with the conditions it ran under.

Coding agents and end-to-end robot policies act through different interfaces. Both tracks share the same tasks, initial conditions and environment-side success checker.

Coding-agent track

No learned policy in the action path

The agent reads the instruction, RGB observations and robot state, and acts through a fixed, non-learned end-effector harness with bounded motion and an explicit give-up.

Ground-truth scoring state is never returned to the model. Results that use privileged poses, additional sensors or extra development episodes are reported as separate, labelled conditions.

What an episode fixes

An evaluation instance is fully specified before it starts.

  • Task definitionOne of the 30 tasks
  • DifficultyEasy, Medium or Hard
  • Initial conditionFrom a frozen distribution
  • External-event seedTiming of arrivals and disturbances
  • Observation permissionsWhat the system may see
  • Declared budgetsTime, actuator steps, model and tool calls
  1. Fresh start. Each episode begins with a fresh runtime or policy state and no cross-episode experience on the target task. History within the episode is allowed, and the Mind tasks require it.
  2. Every started episode counts. Aborted and unsuccessful episodes are kept. A timeout after a valid start is a task failure.
  3. Setup failures are not zeros. An unavailable model or a setup that fails before the episode starts is recorded as missing coverage, not as a success rate of zero.
  4. Independent scoring. Success is decided by the environment-side checker, not by the system's own report.
  5. Full timing logs. Logs keep observation capture, inference start and end, action dispatch and completion, feedback delivery and episode end, so each effect can be traced to the command that caused it.

Metrics

Every result reports two separate measurements. They are not interchangeable.

Score 0–100

Task performance, combining final success with verified stage progress.

Success %

Successful episodes divided by valid started episodes.

0 vs — A measured zero is a result. A dash means not yet evaluated; it is neither zero nor an estimate.

SRt = (1 / Nt) · Σ st,i  // task t, N valid started episodes
SRsuite = mean of SRt over the suite's tasks
SRmacro = (SRMind + SRAct + SRMind2Act) / 3

Task results are computed for a fixed difficulty first; any aggregate over difficulty uses a weighting fixed in advance. A suite or overall value stays empty until its coverage is complete, and a task that carries several capability tags is counted once.

Progress is credited at task-defined checkpoints whose effect has been verified and is still valid at the end of the episode. A later disturbance can revoke a checkpoint, so progress is not the number of commands sent or the best stage ever reached.

Diagnostic measurements

Final success alone cannot show where a long-horizon episode broke down. These behavioural measurements locate the failure.

MeasurementWhat it captures
Premature advancementMoving on to a dependent step before the current physical condition is met.
State mismatchContinuing from a stale or wrong task state, such as treating a missed deposit as delivered.
Wrong-target bindingA valid physical execution on the wrong object, container, route node or frame.
Physical residualTask-specific error: position or angle, insertion depth, delivered quantity, contact time.
Recovery costExtra actions, time and resources spent after a detected deviation.
Latency and update rateTime from an observation to its command, and independently produced commands per second of active time.

Where a system's interfaces can be replaced, matched runs separate decision from execution: Reason-Only with an oracle executor, Act-Only with oracle subgoals, Coupled for the native system, and Certified as a feasibility reference rather than a model score.

Reporting conditions

A leaderboard row compares complete systems, not equal pretraining or compute. Each row is published with the conditions below.

  • Exact checkpointIdentity of the evaluated model
  • Training conditionsAny Mind2Act training or fine-tuning data
  • Observation permissionsCameras, state, extra sensors
  • Action interfaceHarness or action mode, chunk duration
  • Execution assistanceTools and controllers in the loop
  • Budget and clockLimits, clock condition, API calls and cost

    Open an issue with the system, its track and the conditions it needs.

    Connect a harness, or an adapter for the XPolicyLab lifecycle.

    Fix the checkpoint and configuration before the evaluation round.

    Run on the same task configurations as every other entry, with all episodes kept.
